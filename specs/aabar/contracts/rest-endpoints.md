# REST Contract — AABAR Webhook Endpoints

All three endpoints target the same **n8n webhook** at a base URL stored in Firestore `config/*` → `aabar_webhook_url`. The exact URL is out of mobile scope; the mobile app reads it from `ConfigCubit.state.aabarWebhookUrl`.

Authentication on all endpoints: the existing `NetworkInterceptor` adds `Authorization: Bearer <accessToken>` automatically. The n8n side validates this token against the Criarte auth service.

---

## POST `<webhookBase>/chat`

Primary chat turn endpoint.

### Request

**Headers** (added by `NetworkInterceptor` automatically):
```
Authorization: Bearer <accessToken>
school: <schoolName>
school_id: <schoolId>
lang: pt | en | ar
Content-Type: application/json
```

**Body** (default — no child context):
```json
{
  "prompt": "Como ajudo meu filho a se acalmar durante o meltdown?",
  "role": "parent",
  "school_id": 42,
  "lang": "pt"
}
```

**Body** (with child context — only when consent tick was ON):
```json
{
  "prompt": "Interprete este registro em chave de ABA.",
  "role": "teacher",
  "school_id": 42,
  "lang": "pt",
  "child_context": {
    "child_id": 7,
    "recent_activities": [
      {
        "id": "12345",
        "professor": { ... },
        "date": "2026-05-16",
        "categories": [ ... ]
      }
    ],
    "consent_token": "cst_abc123xyz"
  }
}
```

`role`: derived from the active flavor at login (`UserBloc.state.user.type`). The webhook may tailor its response style (e.g., more technical for `teacher`); the mobile app does not branch on the response.

`school_id`: from `UserBloc.state.user.schoolId`.

`lang`: from `ConfigCubit.state.lang` (user's selected language: `"pt"` | `"en"` | `"ar"`).

`child_context.recent_activities`: structured `Activity` objects from the last 7 days for `child_id`. Each `Activity` is serialized via `Activity.toJson()` — same format as the diary REST API. The webhook is responsible for extracting relevant fields.

### Response

**Success (`200`)**:
```json
{
  "answer": "Durante um meltdown, a primeira coisa..."
}
```
`answer` is a plain-text string that may contain markdown (lists, bold, `**text**`, `- item`). The mobile renders it with `MarkdownBody`. No other required fields. Anticipated future optional fields (`citations`, `corpus_version`) are silently ignored by v1.

**Errors**:

| Status | Mobile action |
|--------|---------------|
| `400` | Flip user bubble to error state (reason: `server`). Log to Crashlytics (redacted). |
| `401` | Flip user bubble to error state. Trigger token-refresh via existing auth flow if available; otherwise surface generic error. |
| `403` | Flip user bubble to error state. Likely: `consent_token` does not cover this `child_id`. Surface generic server error (do not expose the 403 reason text). |
| `429` | Flip user bubble to error state (reason: `rateLimit`). Read `Retry-After` header for `retryAfterSeconds`. Render localized cool-down message. Composer remains **enabled**. |
| `5xx` | Flip user bubble to error state (reason: `server`). |
| Timeout (>30 s) | Flip user bubble to error state (reason: `timeout`). |
| Network unreachable | Flip user bubble to error state (reason: `offline`). |

No auto-retry on any failure. User taps "Tentar novamente" to re-send.

## POST `<webhookBase>/consent-token`

Issues a single-use, short-lived consent token authorizing the attachment of a specific child's diary context to one message.

Called **inline before** `POST /chat` when the child-context tick is ON. Mobile must not cache the token.

### Request

**Headers**: same as `/chat` (added by `NetworkInterceptor`).

**Body**:
```json
{
  "child_id": 7,
  "idempotency_key": "uuid-v4-per-compose-session"
}
```

`idempotency_key`: UUID v4 generated by `AABARCubit` at compose-session start. The server uses this to deduplicate retries (e.g., user taps "Tentar novamente" on a consent-fetch failure). Same key is used for both the `/consent-token` call and the subsequent `/chat` call in the same send attempt.

### Response

**Success (`200`)**:
```json
{
  "consent_token": "cst_abc123xyz",
  "expires_in": 60
}
```

`expires_in` is informational (seconds). The mobile does not enforce this TTL client-side; it simply uses the token immediately in the subsequent `/chat` call. A stale token surfaces as a `403` from `/chat` (server enforces expiry).

**Errors**: Same error handling as `/chat`. If `/consent-token` fails, the send fails at this step and the user bubble flips to an error state without ever calling `/chat`.

## POST `<webhookBase>/erase`

Server-to-server erasure trigger. Fired from the existing settings "Delete my data" / "Delete my account" path.

### Request

**Headers**: same as `/chat`.

**Body**:
```json
{
  "user_id": "<Firebase Auth UID>"
}
```

### Response

**Success (`200` or `204`)**: Mobile does not poll for result. Fire-and-forget. The AABAR backend removes all stored conversation transcripts and consent ledger entries for this user.

**Failure**: Logged to Crashlytics; the mobile "Delete account" flow does not block on this result. The server-side cleanup is eventually consistent — the AABAR team should implement a retry queue.

## GET `<webhookBase>/consent-list`

Returns all consent ledger entries for the current authenticated user within the 90-day retention window.

### Request

**Headers**: same (including `Authorization`). No body.

**Query parameters** (optional, for pagination in v1.x):
- `page`, `page_size` — not implemented in v1; server returns all within window

### Response

**Success (`200`)**:
```json
{
  "entries": [
    {
      "consent_token": "cst_abc123xyz",
      "child_id": 7,
      "child_name": "Lucas",
      "issued_at": "2026-05-16T10:30:00Z",
      "used_at":   "2026-05-16T10:30:02Z",
      "revoked_at": null
    }
  ]
}
```

Mobile maps this to `List<AABARConsentLedgerEntry>`. Entries with `revoked_at` non-null are shown with a "Revogado" badge (not hidden) so users can see their full history.

---

## POST `<webhookBase>/consent-revoke`

Revokes a single consent token and removes the associated `child_context` payload from the retained transcript.

### Request

**Headers**: same.

**Body**:
```json
{
  "consent_token": "cst_abc123xyz"
}
```

### Response

**Success (`200`)**: Cubit updates the local entry's `revokedAt` to `DateTime.now()` optimistically; re-fetches the full list from the server on success to confirm.

**Failure**: Surface generic error toast; do not optimistically update the entry. User can retry.

## Notes for backend / n8n team

1. The `Authorization: Bearer` token is the existing Criarte `accessToken` issued at Firebase Auth login. The n8n side must validate it against the Criarte verification endpoint (or share a signing secret). Coordinate with the Criarte backend team.
2. The `school`/`school_id` headers are added by the mobile interceptor and are redundant with the `school_id` field in the body — the server can use either.
3. The `child_context.recent_activities` array may be large for busy diary users. The server should extract only the fields it uses for the RAG context and not echo the full array back.
4. The `idempotency_key` in `/consent-token` must be stored server-side with a ≥ 24 h dedup window (same pattern as `diary` idempotency — see specs/diary/research.md R7).
5. LGPD audit requirement: the server must log every `/consent-token` issuance and `/consent-revoke` revocation with timestamp + user_id + child_id. The mobile audit screen reads this log via `/consent-list`.
