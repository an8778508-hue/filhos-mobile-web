# Quickstart: AABAR — in-app ABA chat agent

How to pick up the AABAR implementation. Read order: [spec.md](spec.md) (the *what*) → [plan.md](plan.md) (the *how/sequence*) → [research.md](research.md) (resolved unknowns) → [data-model.md](data-model.md) + [contracts/](contracts/) (the shapes) → tasks.md (the checklist, generated by `/speckit.tasks`).

## Before you write any AABAR code — one prereq

**T-setup-1** — add `flutter_markdown: ^0.7.x` to `pubspec.yaml` and run `flutter pub get`.

`flutter_markdown` is not in the codebase today (confirmed by grep). All AABAR assistant bubbles use `MarkdownBody`; the dependency must be present before any UI work starts. `flutter analyze` will fail on both flavors without it.

## Smoke tests per wave (no `test/` dir — manual, both flavors)

- **Wave 2**: Log in approved parent → tap AABAR section tile → empty chat with disclaimer, no chips yet → type "Olá" → send → typing indicator → reply bubble → close app → reopen → fresh chat (no prior messages).
- **Wave 3**: Same flow → confirm 4 chips appear when list is empty, disappear after first message → tap chip → text fills composer, not auto-sent → edit and send.
- **Wave 4**: Tick child-context checkbox → if parent has 2 children, child-picker appears → select one → send → network log shows `child_context` in body → reply → next compose: tick is OFF again.
- **Wave 5**: Open a diary entry → see "Pedir interpretação à AABAR" action → tap → AABAR chat opens → composer pre-filled with seed text → child-context affordance is ON and highlighted → can untick → send both ways → verify payload has / doesn't have `child_context` as expected.
- **Wave 6**: Settings → "Meus consentimentos AABAR" → see list of tokens → tap "Revogar" on one → entry updates to "Revogado" → empty state shows when no entries.
- **Wave 7**: Delete account path → confirm erasure call fires to `/erase` (inspect network or server log) → Crashlytics staging: confirm no prompt text in breadcrumbs.

## Rate-limit edge case (Wave 2 / integration testing)

Simulate a `429` response from the mock or staging webhook with `Retry-After: 10`. Confirm:
- User bubble flips to error with localized cool-down text `aabar_error_rate_limit` (not a generic error)
- Composer remains enabled
- Sending another message before the 10 s window returns another `429` (not a client-side block)
- "Tentar novamente" on the errored bubble re-sends the same message

## Known limitations carried into v1

- AR translations of the 25 `aabar_*` keys are TBD (localization team). PT-BR + EN ship; AR placeholder keys are present so AR users see the key name rather than crashing.
- No streaming response — each reply waits for the full `answer` string before rendering.
- Firestore offline persistence is globally disabled app-wide — not a concern for AABAR (uses REST, not Firestore).
- The open business decision (single org-wide webhook vs per-school URL) is deferred; the `aabar_webhook_url` field accommodates both.
- NPS prompt (SC-009: once per 30 days per user) is deferred to v1.x. Not blocking launch.

## Backend coordination

Open one umbrella ticket with the AABAR / n8n team covering:
1. Accept Criarte `Authorization: Bearer` token (validate against Criarte auth service or shared secret).
2. Implement `/chat` with default + child-context body variants.
3. Implement `/consent-token` with idempotency (≥ 24 h dedup window on `idempotency_key`).
4. Implement `/erase` (fire-and-forget from mobile; server should have a retry queue).
5. Implement `/consent-list` + `/consent-revoke` for the audit surface.
6. Add `aabar_webhook_url` to the Firestore `config/{schoolId}` document per school.
7. LGPD audit log for every consent issuance and revocation.
